# CLAUDE.md

Project context for Claude Code. For full details, see `BLUEPRINT.md`.

## Project

TuturEdu — chat platform for a tuition centre (FYP, Politeknik METrO Tasek Gelugor).
Roles: **Student**, **Teacher**, **Parent**. Chat is locked outside office hours.

## Stack

- Flutter (mobile + web)
- Firebase: Authentication, Cloud Firestore, Storage, Hosting, Cloud Functions (2nd gen, `asia-southeast1`) — project is on the Blaze pay-as-you-go plan
  - Storage bucket: `tuturedu-app.firebasestorage.app` (US-EAST1, no-cost location — Firestore itself is `asia-southeast1`, different region is fine, they're independent products). `storage.rules` deployed — file attachments work end-to-end.
  - `storage.rules`'s `write` rule for `chats/{chatId}/attachments/{fileName}` deliberately does NOT check `firestore.get(...).data.participants` (unlike `read`, which does). Confirmed by testing: on Flutter **Web**, that cross-service check fails every single time on write — Web's resumable-upload protocol evaluates Storage rules during the session-start request, where `firestore.get()` doesn't reliably resolve (same category of bug as the `request.resource.size` check also removed from this rule — see the rules file's own comments). `write` is relaxed to `request.auth != null`; this is safe in practice because `firestore.rules`' `messages/{messageId}` create rule (an ordinary Firestore write, unaffected by this Storage-side quirk) still requires the sender to be a genuine chat participant, so a non-participant "uploading" here can never make a file appear as a real message to anyone. If you ever need to re-tighten Storage write rules, do NOT reintroduce a `firestore.get()`/`firestore.exists()` check without testing a Web upload specifically — this exact bug will silently return.
  - The Web upload itself was never actually the flaky part, despite looking like it — confirmed via DevTools that the request throwing `storage/unauthorized` and surfacing as "Upload failed" is a **GET**, not the PUT. `_pickAndSendAttachment()` calls `storageRef.getDownloadURL()` right after the upload finishes, and that call re-evaluates the rule's `allow read` clause (the one that cross-checks `firestore.get(...).data.participants`) — the same firestore.get()-during-a-Storage-request unreliability documented on the `write` rule above also hits this GET occasionally, immediately after a resumable upload session closes. This is why `allow write: if true` didn't fix anything when tested — write was never the failing rule — and why a fix aimed only at the upload step (retrying `putData`, forcing `getIdToken(true)` before it) didn't help either: the failure was one step later. `chat_screen.dart` now wraps `getDownloadURL()` itself in the same refresh-and-retry loop (up to 3 attempts, `getIdToken(true)` + 700ms between). If uploads ever appear to fail again, check which request in DevTools actually 403s (GET vs PUT) before assuming it's the rule you last touched.
  - `functions/` is a separate Node.js project (not Dart/Flutter) — `npm install` inside it before deploying. Sends push notifications; see Status below for the one manual step still needed for Web.
- Live: https://tuturedu-app.web.app/

## Conventions

- **Claymorphism**: the app's visual style is soft/puffy "clay" surfaces (dual-direction shadow: a dark "sunken" shadow one side + a light "highlight" the other, via `main.dart`'s `clayShadows(context, {intensity})`) instead of a single flat Material shadow or a contrasting white card. Surface fill colors (`kClaySurfaceLight`/`Dark`, `Theme.of(context).cardColor`) are deliberately close to the scaffold background (`kClayBaseLight`/`Dark`) - the puffy look comes entirely from the shadow pair, not color contrast. Buttons/icons stay solid/saturated brand blue/green (no clay treatment on those - accent elements, not surfaces) per the chosen direction. `AppCard`/`IconTile`/`StatTile`/`MenuRow`/`MessageBubble` (the "other" bubble only - the sent bubble stays solid blue) all call `clayShadows()`; add it to any new raised surface rather than a one-off `BoxShadow`. Not touched: the Interactive Quiz's own gameplay screens (see next bullet) - their existing flat shadows are that module's own deliberate style.
- **UI/UX design system** lives in `lib/widgets/` (`AppCard`, `IconTile`, `StatTile`, `SectionLabel`, `EmptyState`, `LinearStatBar`, `MenuRow`, `DashboardHeader`, `MessageBubble`) — reach for these instead of hand-rolling another `Card`/`Container`+shadow/empty-state Column. `TeacherDashboard`/`StudentDashboard`/`ParentDashboard` render a `DashboardHeader` (stat row + quick-action grid) above their `ChatListScreen` via its `homeHeader` builder param — don't add more AppBar icons for new dashboard actions, add a `QuickAction` to that header instead. `ChatListScreen` no longer has a `tabBarTrailing` param (removed - it duplicated the exact same actions the `DashboardHeader` below it already surfaces, which a user screenshot caught as visual clutter); its `TabBar` (All/Individual/Groups) is a rounded pill-segmented control (a translucent-black track + white sliding pill indicator) instead of a plain underline, sitting inside the `AppBar`'s `bottom:`. Not touched by this design pass: the Interactive Quiz's own purple/game-show palette (`lib/utils/quiz_theme.dart`) and any screen that paints `QuizTheme.pageGradient` as its body background — `attempt_quiz_screen.dart`, `host_quiz_session_screen.dart`, `live_quiz_play_screen.dart`, `join_quiz_screen.dart`, `quiz_leaderboard_view.dart`, **and also** `quiz_list_screen.dart`, `self_paced_quiz_list_screen.dart`, `create_quiz_screen.dart` — that Kahoot-style identity is deliberate and separate from general app chrome. **Real regression this caused once**: those last 3 aren't "gameplay" screens so it's easy to forget they're on the same fixed gradient - during the Dark Mode pass they got `AppCard`/`Theme.of(context).textTheme...`-based (theme-following) colors like every other screen, which put light/theme-derived text on a background that never actually gets dark, making it nearly invisible in dark mode (caught via a user screenshot on Self-Paced Quizzes). Any text/card color on these 3 files must stay a fixed literal (`Colors.black87`/`Colors.black54`, `Colors.white` card fill, etc.), never `Theme.of(context)`-derived or the shared `AppCard`/`EmptyState` widgets' default (theme-following) colors. The first fix pass only patched the specific colors a screenshot had caught, then a second screenshot (`create_quiz_screen.dart`, its `ChoiceChip`s/`TextField`/`TextFormField`s never set an explicit fill/text color) showed the same trap hiding in every default-styled input widget too - patching widgets one at a time doesn't scale. The actual fix: all 3 files now wrap their `Scaffold`'s `body:` in `Theme(data: ThemeData.light(useMaterial3: true), child: ...)`, forcing every descendant's *default* colors (hint/label/input text, unselected `ChoiceChip` fill, anything not given an explicit color) to resolve against a light theme no matter the app's Light/Dark/System setting - do this for any new fixed-gradient quiz screen too, rather than chasing individual widget colors.
- **Dark Mode**: account-level setting (`users/{uid}.themeMode`, `"light"`/`"dark"`/`"system"`, default `"system"`), toggled from Settings' "Appearance" section — NOT a per-device/local preference, so don't reach for `SharedPreferences` for this. `main.dart`'s `_MyAppState` listens to `FirebaseAuth.authStateChanges()` and, per signed-in user, subscribes to their `users/{uid}` doc to keep the global `themeModeNotifier` (a `ValueNotifier<ThemeMode>`) in sync — that's what actually drives `MaterialApp`'s `themeMode:`, wrapped in a `ValueListenableBuilder`. `lib/utils/theme_preference.dart` holds the `String`↔`ThemeMode` mapping shared by both ends. Any new widget with an explicit color (not inherited from `Theme.of(context)`/`TextTheme`) needs a light AND dark value or it'll look broken in one mode — the shared widgets above already handle this (e.g. `AppCard`'s `color` defaults to `Theme.of(context).cardColor`, not a hardcoded white). `WelcomeScreen`/`LoginScreen`/`RegisterScreen`/`MfaVerificationScreen` run before any account is known, so they follow the device's system theme (via `themeModeNotifier`'s `ThemeMode.system` default when signed out) rather than an account preference - they were originally left with hardcoded light-only colors, but that broke visibly (bright white login card while the rest of the app is dark) so they now pull from `Theme.of(context)`/`welcome_screen.dart`'s own `_inkDark(context)`/`_inkMuted(context)`/`_borderColor(context)` helpers too. The one deliberately-still-fixed piece is `WelcomeScreen`'s navy "About the Centre" panel (solid dark bg + white text, via the `_kInkDark`/`_kInkMuted` constants) - a highlight block that's supposed to look the same regardless of theme, not a bug.
- **Recurring dark-mode trap**: a background painted with `Colors.xxx.shade50`/`shade100`/`shade200` (opaque, always-light, e.g. the old quick-reply chip and `group_info_screen.dart`'s header) does NOT get darker in dark mode - if the text on it uses an inherited/theme-derived color (or no color at all), that text goes light-on-light and disappears. Either give both the background AND its text a fixed color pair (the locked-chat banner's `Colors.orange.shade100` bg + explicit `Colors.black87` text is correct and deliberate), or better, make the background itself theme-relative via `color.withValues(alpha: 0.06-0.12)` (blends with whatever's underneath, adapts automatically) and then let the text inherit normally - that's the pattern `StatTile`/`AppCard`-based percentage panels use. When fixing a contrast bug, check which pattern the container already uses before changing just the text color, or you can end up "fixing" it backwards.
- Role value in Firestore is `"Teacher"`.
- Class/subject format: `"Subject Level"` string, e.g. `"Add Maths Form 4"`. No department/program/classGroup fields.
- Office hour: global, Mon–Fri 9AM–5PM, logic lives in `lib/utils/office_hours.dart`. Always call `OfficeHours.isOfficeHourNow()` — never hardcode time checks elsewhere.
  - Has a `debugForceOpen` flag guarded by `kDebugMode` for testing. Keep the guard — don't remove it.
  - `chat_screen.dart` doesn't use `isOfficeHourNow()` directly for gating — it wraps it in `_computeIsOfficeHour()`, which also folds in the chat's teacher's manual On-Duty/Off-Duty status (`users/{uid}.dutyStatus`) and Leave/Holiday date range (`leaveStart`/`leaveEnd`, set from Settings). Use that wrapper, not the raw office-hours check, anywhere chat-lock state is computed.
- App root is `lib/screens/auth_gate.dart` (`AuthGate`), not `WelcomeScreen` directly — `main.dart`'s `home:` points there. It's a `StreamBuilder` on `FirebaseAuth.authStateChanges()`: if a session already exists it fetches `users/{uid}.role` and routes straight to the matching dashboard, only falling back to `WelcomeScreen` when signed out (or the Firestore user doc is missing, in which case it signs out the dead session first). Without this, `home:` being hardcoded to `WelcomeScreen` was the cause of a real bug — Firebase Auth already persists sessions across app restarts, but the UI ignored that and always re-prompted for login.
  - Web is deliberately excluded from this persistence: `main.dart` calls `FirebaseAuth.instance.setPersistence(Persistence.NONE)` when `kIsWeb`, before `runApp()`, so the Web build always needs a fresh sign-in on reload/reopen (shared/public browser assumption) while Android/iOS keep the normal persisted session (`setPersistence` no-ops on native).
- There is no standalone "About" page — a prior version (`about_arena_matriks_screen.dart`) was removed; its content (story, "What We Offer", Operating Hours via `OfficeHours.officeHourText()`) now lives inline in `welcome_screen.dart` itself, continuing directly below the Log In/Sign Up buttons on the same scrollable page rather than a separate route. `login_screen.dart`'s existing Arena Matriks blurb is separate, pre-existing content — leave it as is.
- `WelcomeScreen` has two separate Log In/Sign Up entry points, both intentional: small `TextButton`s in a top-right quick-access bar (for a returning user who wants to skip straight past the branding), and the full-size `ElevatedButton`/`OutlinedButton` pair lower on the page. Keep both in sync if either destination route ever changes. The page is now fairly long (hero + About content + social footer), so it's wrapped in a `LayoutBuilder` + `SingleChildScrollView` + `ConstrainedBox(minHeight: ...)` — that combination centers short content but scrolls instead of clipping when it doesn't fit; don't revert to a plain non-scrolling `Column` here, that was the cause of a real bug (About content silently pushed off-screen).
- `WelcomeScreen`'s footer links out to the centre's real social accounts (Facebook/Instagram/TikTok URLs hardcoded in `_socialLinks`) via `url_launcher`. Icons come from the `font_awesome_flutter` package (added for this — Material Icons has no Instagram/TikTok logo). That package's `FontAwesomeIcons.*` constants are `FaIconData`, NOT `IconData` — they only render via the `FaIcon` widget, not the standard `Icon` widget; mixing them up is a compile error, not a runtime one, so it's easy to catch but worth knowing going in.
- Navigation: always route post-auth screens with `pushAndRemoveUntil` (not `pushReplacement`) — `login_screen.dart`/`register_screen.dart` do this so `WelcomeScreen` never stays buried at the bottom of the stack. A stray `Navigator.popUntil(context, (route) => route.isFirst)` anywhere would otherwise land back on the login page even with a valid session (this exact bug happened once in the quiz leaderboard's "Done" button — see BLUEPRINT.md 5.13).
- Chat ID format: `{uid1}_{uid2}` with UIDs sorted alphabetically (see `user_search_screen.dart`).
- Messages are create-only, with ONE narrow exception: soft-delete (rujuk `firestore.rules`' `messages/{messageId}` `allow update`). Long-press a bubble in `chat_screen.dart` sets `deleted: true` + `deletedAt` — never any other field, and never a real `delete`. Sender can do this within 15 minutes of sending (`_deleteWindow`); Admin can do it any time. The rule itself re-checks both conditions server-side (`diff().affectedKeys().hasOnly(['deleted', 'deletedAt'])`, the time window, and `isAdmin()`) — never trust the client-side `_canDeleteMessage()` check alone, it's UX-only. Original content is never cleared from Firestore, just hidden behind the `deleted` flag — deliberate, keeps an audit trail (see BLUEPRINT.md 5.16 for the full rationale).
- `TeacherDashboard`/`StudentDashboard`/`ParentDashboard` are thin wrappers around `ChatListScreen` (configured with role color + FAB) — they are the chat list itself, not a menu screen in front of it.
- Parent↔Student linking (`users/{uid}.parentUid`/`childUids`) is Admin-only, done via `link_parent_child_screen.dart` — there's no self-service way for a Parent to link their own child (by design, avoids anyone claiming to be any student's parent). A Student has exactly one `parentUid`, but a Parent's `childUids` is an **array** (`FieldValue.arrayUnion`) — one parent can have 2+ children linked. `child_overview_screen.dart` shows a child picker in the AppBar once there's more than one; `manage_users_screen.dart`'s "Manage Children" action lets an Admin unlink one child at a time without touching the others. `firestore.rules`' `attendance` rule checks `studentUid in ...childUids` (not `==`) for this reason — if you ever touch that rule, keep it as an array membership check.
- Quiz `mode` is `"live"` | `"self_paced"` | `"both"`, chosen by the teacher in `create_quiz_screen.dart`. `quizAttempts/{quizId}_{studentUid}` (Self-Paced) uses a deterministic doc ID — same pattern as `attendance/{studentUid}/records/{subject}_{date}` — to get "already attempted?" checks down to a single `get()`, no query/index needed. Firestore only allows one `whereIn`/`in` clause per query, so `self_paced_quiz_list_screen.dart` filters on `mode` server-side and the student's own subjects client-side.
  - **`resource == null` trap bit this project once already here**: `quizAttempts`' old `allow read` rule checked `resource.data.studentUid` directly, with no guard for the very first read (before any attempt doc exists) — Firestore rule evaluation errors on a null `resource`, which is treated as denied, and `attempt_quiz_screen.dart`'s `_load()` had no try/catch, so a first-time quiz open just spun forever with no error shown ("loading non-stop", reported by a user). Fixed the same way `attendance`'s rule already was: `resource == null || ...` first in the `||` chain. If you ever add a new collection with a deterministic/"check before create" doc ID pattern, give its read rule this same guard up front — don't wait for it to bite twice.
  - Self-Paced quizzes support retake (`quizzes.maxAttempts`, default `1` = no retake) and an optional due date (`quizzes.dueDate`), both set in `create_quiz_screen.dart`. `attempt_quiz_screen.dart` tracks `quizAttempts.attemptsUsed` and overwrites the same attempt doc on every retake — no per-attempt history is kept, only the latest submission. `quiz_results_screen.dart` (Teacher, reachable from `quiz_list_screen.dart`'s "View Results" icon) lists every enrolled student's Self-Paced result for one quiz — Live Session scores live in `quizSessions/{sessionId}/participants` instead and already have their own leaderboard, so they're intentionally not shown there. `quizAttempts`' read rule also allows the quiz's own `createdBy` teacher (via a `get()` on `quizzes/{quizId}`), not just the attempt's owner/Admin, specifically so this results screen can query across all students' attempts.
  - `create_quiz_screen.dart` doubles as the Edit Quiz form: an optional `quizId` constructor param (`null` = create, non-null = edit) drives `_init()`, which loads the existing quiz doc + its `questions` subcollection and pre-fills every field/draft before the form renders. Saving in edit mode always fully replaces the `questions` subcollection (delete every existing question doc, then re-add current drafts) rather than diffing individual questions — same write pattern as create, just wrapped in `batch.update` instead of `batch.set` for the quiz doc itself. No `firestore.rules` change was needed: the existing `quizzes/{quizId}` rule (`allow update, delete: if request.auth.uid == resource.data.createdBy`) already covers the creating teacher editing their own quiz and its questions. Reached via an Edit icon on each row in `quiz_list_screen.dart`.
- Push notifications: Firestore can't call the FCM API directly — that's *why* `functions/` exists at all. `lib/utils/push_notifications.dart` only ever writes/removes this device's token to/from `users/{uid}.fcmTokens`; the actual sending happens in `functions/index.js`'s Firestore triggers. Web Push is live — `_webVapidKey` is filled in and the web build carrying it has been deployed. That key (Firebase Console → Cloud Messaging → Web configuration → "Generate key pair") is human-only, no CLI equivalent — keep that in mind if it ever needs regenerating.
- Self account deletion (Settings screen) is fully client-side — Firebase lets a user delete their *own* Auth account with no Admin SDK. Don't confuse this with Admin deleting *someone else's* account (Manage Users), which still needs the Cloud Function noted below.
- Admin "Delete User" (`manage_users_screen.dart`) calls the `deleteUserAccount` callable Cloud Function (`functions/index.js`, region `asia-southeast1`) — deletes both the Firestore `users/{uid}` doc and the Firebase Auth account in one call. The function re-checks caller-is-Admin server-side (`users/{callerUid}.role == 'Admin'`) before doing anything; never trust a client-side role check alone for this. Client SDK genuinely cannot delete another user's Auth account (only your own, see self-delete above) — that's why this needs a Cloud Function at all.
- Assigning subjects to a Student is no longer Admin-only: `user_profile_screen.dart` gives a Teacher viewing a Student's profile an Edit action on the Subjects row (`canEditSubjects = viewerRole == 'Teacher' && role == 'Student'`, resolved via a `_ProfileData` that bundles both the target's and the viewer's own doc in one `FutureBuilder`). `firestore.rules`' `users/{userId}` write rule has a matching `isTeacher()`-gated clause restricted to `request.resource.data.diff(resource.data).affectedKeys().hasOnly(['subjects'])` — a Teacher can change ONLY that field on a Student's doc, nothing else, same field-restriction pattern as `warningLetters.acknowledged`. A Teacher's own subjects are separately self-editable from a "My Subjects" section in Settings (writes to their own doc, no rules change needed for that half).
- Notification sound: 3 choices defined once in `lib/utils/notification_sounds.dart` (`notificationSoundOptions` + `defaultNotificationSoundId` = `option2_marimba`), selected in Settings and stored on `users/{uid}.notificationSound`. Each option's `id` doubles as the filename (`assets/sounds/{id}.mp3` for Flutter playback via `audioplayers`, and `android/app/src/main/res/raw/{id}.mp3` — a separate copy — for the Cloud Function to reference as `android.notification.sound` in the FCM payload). `functions/index.js` has its own `DEFAULT_SOUND` constant that must be kept in sync with the Dart default by hand (JS/Dart can't share a literal). Web Push has no cross-browser API for custom background sound, so this only fully works end-to-end on Android; foreground playback (any platform, app open) works via `playNotificationSoundForCurrentUser()` in `main.dart`'s `FirebaseMessaging.onMessage`.
- Android app icon is TuturEdu's own mark (all 5 `mipmap-*/ic_launcher.png` densities), not the Flutter default. `applicationId` is still the placeholder `com.example.tuturedu` and release builds are signed with the debug key — fine for sideloading (`flutter build apk --release`), not set up for Play Store distribution.
- URL phishing detection in chat (`lib/utils/phishing_detector.dart`, rendered in `chat_screen.dart`'s `_buildMessageText()`) is heuristic-only, client-side, no external API — flags raw-IP hosts, the `@` URL trick, known shorteners, punycode/IDN, and a short list of commonly-abused TLDs. Only scans message *text*; file attachments are already validated separately (see `file_validator.dart`). This replaced plain `Text(text, ...)` rendering for message bubbles — before this, URLs typed in chat weren't tappable at all.
- **MFA (email OTP) is mandatory for every role on every fresh sign-in** (both `login_screen.dart` and `register_screen.dart`, see BLUEPRINT.md 5.17) — after password auth succeeds, both screens push `MfaVerificationScreen(destination: destination)` instead of `destination` directly; that screen calls the `sendMfaCode`/`verifyMfaCode` Cloud Functions and only then does the real `pushAndRemoveUntil` to the dashboard. Scope limit: this only fires when `signInWithEmailAndPassword`/`createUserWithEmailAndPassword` actually run — `AuthGate` still silently resumes a persisted session on Android/iOS without re-asking (a deliberate trade-off to avoid fighting AuthGate's own persistence feature; Web is unaffected since it already forces a fresh sign-in every time via `Persistence.NONE`). Firebase Auth has no built-in "send a custom OTP by email" MFA option (native MFA there is SMS/TOTP only) — this is a from-scratch implementation: a random 6-digit code, SHA-256-hashed and stored in `mfaCodes/{uid}` (5-min expiry, 5-attempt cap, Firestore rules deny all client access — Admin SDK only), emailed via Gmail SMTP/nodemailer. **Requires manual one-time setup**: a Gmail account with 2-Step Verification on, an App Password from myaccount.google.com/apppasswords, and `firebase functions:secrets:set MFA_SMTP_USER` / `...MFA_SMTP_PASS` run by hand in your own terminal — never paste that password into chat/AI, the whole point of Firebase secrets is that the value only ever passes through your own CLI session. `mfa_verification_screen.dart` has a `debugBypassMfa` flag (same `kDebugMode`-guarded pattern as `office_hours.dart`'s `debugForceOpen`) that skips sending/verifying the code entirely and jumps straight to the dashboard — for local testing only, automatically a no-op in a release build even if left `true`. Like `debugForceOpen`, treat it as a local, uncommitted toggle — don't push it as `true`.
- Login/Sign Up failures never show raw Firebase exception text (e.g. `[firebase_auth/wrong-password] The password is invalid...`) — `lib/utils/auth_error_dialog.dart`'s `showAuthErrorDialog()` maps known `FirebaseAuthException` codes to plain-language messages and shows them in an `AlertDialog` (not a `SnackBar` — a login failure needs to be impossible to miss/dismiss by accident). Deliberately gives the *same* message for `user-not-found` and `wrong-password`/`invalid-credential` ("Incorrect email or password") — revealing which one it was lets an attacker enumerate registered emails. Both `login_screen.dart` and `register_screen.dart` use this; if you add another Firebase Auth call anywhere, route its errors through this too rather than a fresh `catch (e) { ...e.toString()... }`.
- Before implementing new features, check `BLUEPRINT.md` first — it's kept up to date with what's actually built vs. still speced-out (schema, logic flow, status markers ✅/🔲/💡).
